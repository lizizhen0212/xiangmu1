## 1. Git 与 GitHub 是什么

把 **GitHub = Git + Hub** 拆开看：

### Git —— 一个版本控制软件
- 开源免费，是**目前世界上使用人数最多的版本控制系统**。
- 用写论文的日常经验切入：`第一版 → 第二版 → 第三版 → 定稿版 → 最终版 → 打死不改最终版`，小心保存每个版本，就是为了某天能找回"某个历史版本的某个段落"。这就是**最原始的版本控制**——纯人工。
- 一旦项目有成千上万个文件、成百上千人协同，人工方式必然崩溃，于是 Git 诞生。
- **一个文件夹被 Git 管理起来，就成了一个 Git 仓库**，文件夹下会生成 `.git` 子文件夹，存放所有版本控制信息。
- **Commit（提交）是版本控制的基本单元**：每 commit 一次，Git 就保存一份当时仓库状态的**快照**；commit 越来越多，形成一条**可回溯的历史链路**，每个参与者的每次改动都被记录。

### Hub —— 中心、汇聚
- 全世界的开发者把自己用 Git 管理的仓库上传到 GitHub，这个网站就成了 Git 仓库的集合，即 hub。
- **GitHub 是全球最大的代码仓库托管与协作平台**：存储、分享、和别人一起写代码。

### 仓库的两种分法

| 分法 | 类型 | 说明 |
|---|---|---|
| 位置 | **Local Repository 本地仓库** | 跑在自己电脑上的 Git 仓库 |
| 位置 | **Remote Repository 远端仓库** | 传到服务器上用于备份 / 分享；可自建服务器，也可用现成服务（GitHub、GitLab、Bitbucket） |
| 可见性 | **公开仓库** | 全站可搜索，代码开放，所有人可浏览学习并按规则使用 |
| 可见性 | **私有仓库** | 只有自己可见 |

> 托管在 GitHub 上的著名开源项目：**Linux 操作系统、CPython（Python 官方解释器）、NGINX** 等。视频原话：**开源是计算机科学的基石**。学会 GitHub 后，GitLab、Bitbucket 也基本一通百通。

## 3. Commit 提交

### 3.1 `init` —— 初始化

- **把一个文件夹 `git init`，就是让 Git 接管它，使它变成一个 Git 仓库**，这是使用 Git 的第一步。
- VS Code 操作：`Open Folder` 打开任意文件夹（空/非空都行）→ 左侧 **Source Control（源代码管理）** → **Initialize Repository**。
- 完成后文件夹里多出 **`.git` 子文件夹**（存一切与 Git 有关的数据）；**删掉它就等于取消 Git 管理**，文件夹不再是仓库。

### 3.2 `.gitignore` —— 哪些文件不该被管

- `.gitignore` 是一个文件，里面声明仓库中**哪些文件不归 Git 管理**。
- 典型例子：
  - 存密钥的 **`.env`** —— 应安全留在本地，绝不能上传；
  - Node.js 项目的 **`node_modules/`** —— 上万个第三方依赖包，别人 `npm install` 就能有；**注意末尾加斜杠表示这是一个目录**。
- 最佳实践：**项目初始化时就一并创建 `.gitignore`**，一开始就避免误提交。
- 让 AI 做时的提示词：**"把这个目录进行 git 初始化，注意把不需要的内容都排除掉。"** AI 会自动写好 `.gitignore`，把密钥文件、`node_modules` 等排除。

### 3.3 一次提交的完整动作

1. 新建文件（例：`fruits.txt`，写一行"香蕉"）；
2. 左侧 Source Control 出现待提交文件列表（`.gitignore` + 水果清单）；
3. 填 **Commit Message（提交摘要）**——讲清这次提交做了什么；
4. 点 **Commit** → 第一次提交完成。

### 3.4 `discard changes` —— 放弃未提交的改动

- 对某次修改不满意：打开该文件 → **Discard Changes** → 代码回退到上一次提交的状态。
- **AI 编程的核心技巧**：让 AI 每完成一个**小功能点**就 commit 一次，历史记录保存得极好；发现 AI 改得不符合预期，随时 **Discard** 掉它的改动，改提示词让它重做。

### 3.5 看历史：Graph 与 checkout detached

- 下方 **Graph** 面板可看每条历史链路；展开某次 commit 可看它改了哪些文件。
- 想看某次提交当时的代码：在 commit 上右键 → **Checkout (Detached)** → 整个仓库回到该历史版本。
- ⚠️ 这个状态**只适合看代码，不适合改代码**：`detached` 中文叫**分离头指针**，意味着当前不处于任何分支管理中，在此修改很容易把代码搞丢。
- 回到最新：点左下角分支按钮 → 选回 **master**（主干）。

### 3.6 Commit ID（提交哈希）

- 每次提交除了 Commit Message，还有一个 ID：鼠标悬停在 commit 上，能看到"数字+英文"的小编号。
- 该 ID 由 Git 用**哈希算法**自动算出，所以也叫 **Commit Hash**。
- **短 ID vs 长 ID**：复制出来会变长，其实长 ID 的**前 7 位**就是短 ID，功能完全一样，短 ID 更便于记忆。
- **Commit ID 在同一个仓库里绝对唯一** → 跟 AI 沟通时**直接给 ID 最精确**。

### 3.7 三种"后悔药"（重点）

| 手段 | 行为 | 适用场景 | 风险 |
|---|---|---|---|
| **Discard** | 放弃**还没 commit** 的更改 | 本地改动尚未提交 | 低（只丢未提交改动） |
| **Reset**（`git reset --hard <ID>`） | 把仓库**强制回退**到某个历史状态，之后的提交全没了 | 单人分支；被撤销的改动**还没推到远端** | 高。若已推送需 `push -f` 强推覆盖远端，有丢代码风险；**多人协作分支上禁止使用** |
| **Revert**（`git revert <ID>`） | 生成一次**反向提交**来抵消某次 commit，其他提交不受影响 | 只想撤掉某一次提交 | 低、**安全**；多人分支应优先用它 |

**实战 1（reset）**：想让"山竹""苹果"两次提交整个消失、回到"荔枝"状态 → 在荔枝上右键 **Copy Commit Hash** → 对 AI 说 **"把仓库还原到这次提交的状态，它后面的所有提交都不要了"** → AI 底层执行 `git reset --hard`。

**实战 2（revert）**：发现"香蕉改菠萝"那次提交是错的，但不想影响别的提交 → 复制该 commit hash → **"把这一次的提交撤销掉，保持其他不变"** → AI 执行 `git revert`，生成一条反向提交。

**实战 3（diff）**：想比较两次提交改了啥 → 复制两个 commit ID → **"比较一下这两次提交有什么区别、修改了什么内容"** → AI 底层执行 `git diff`，列出改动文件与统计。

> 结论：命令本身（`reset --hard` / `revert` / `diff`）**完全不用记**，记住"我要什么效果"即可。

## 4. Branch 分支

### 4.1 分支的本质

- **Branch = 存储库的不同开发线**。默认每个仓库都有一条 `main`（视频中为 `master`）分支，即**主干**。
- 创建分支 = 创建一个副本。**补充**：Git 里建分支是靠**指针**实现的，**并不真的拷贝代码**。
- 在 `feature` 分支上改代码并 commit，**这些提交只存在于 feature 上**；切回主干就看不到——**各分支的修改互不影响**。
- 分支对**多人 / 多 agent 协作**极其有用：每个人或每个 agent 开自己的分支做功能，做完再合并回主干。

### 4.2 基本操作

- 左下角显示当前分支（`master`）→ 点击 → **Create New Branch** → 命名 `feature`（基于 master 最新提交创建）。
- 左下角名称变为 `feature` 即表示身处该分支；点它可在分支间来回切换。
- **合并**：对 AI 说 **"把 feature 合并进 master"** → 底层 `git merge` → 主干上就能看到那次提交了。
- **删除分支**：Git **不允许删除当前所在分支**，先切回 master → 右键分支 → **Delete Branch**。

### 4.3 从历史提交创建分支（比 detached 更好的回退方式）

- 不只能基于 master 建分支，也能**基于任意一次历史提交建分支**：找到"芒果"那次提交 → **Create Branch** → 命名 `feature2` → 仓库文件回到那次提交的状态。
- 也能**基于任意一个分支**建分支：基于 `feature` 建 `feature2`，会包含 feature 与 master 上所有代码；而基于 master 建 `feature3`，则只能看到 master 的代码。

### 4.4 回退历史的两种方法对比

| 方法 | 做法 | 特点 |
|---|---|---|
| 分离头指针 | 右键 **Checkout (Detached)** | 只读查看；**不要修改**，容易丢代码 |
| 基于历史提交建分支 | 在 commit 上 **Create Branch** | 代码有分支管理，**可自由修改、不会丢** ✅ |

### 4.5 HEAD 是什么

> **HEAD = 当前仓库处于哪一次 commit 上。**

- 切到 master → HEAD 指向 master 的最新提交（如 commit3）；
- 切到 feature3 → HEAD 指向 commit7；
- 切到 feature → HEAD 指向 commit5；
- 特殊情况：HEAD 不指向任何分支，而指向某一次历史提交 → 就是前面演示的 **checkout detached / 分离头指针**状态。

## 5. WorkTree 工作树

### 5.1 是什么

- `git worktree` 本质是：**建一个新分支 + 把该分支的代码完整复制到一个新文件夹**，这个新文件夹就是一个 worktree。
- 主文件夹和 worktree 文件夹可以**并行工作**，各自改代码、互不干扰；
- 它们底层通过 Git 关联，**worktree 的改动可以轻松合并回主干**。

### 5.2 两种 AI 工具里的用法

- **Codex**：在项目上右键 → **创建永久工作树** → 给分支起名 → 创建 → Codex 把工作树放进一个全新文件夹，随便开发测试都不影响主干；做完让 AI 把工作树合并回主干。
- **Claude Code**：在项目文件夹"在终端中打开" → 执行 `claude --worktree` → 填分支名（例 `AddCoconut`）→ 启动后即处于该 worktree，界面会显示 worktree 目录。
  - 演示：让 Claude Code "给水果清单添加椰子" → worktree 里有了椰子，**主文件夹没有** → 让它提交并合并回主干 → 最后删除该 worktree（底层 `git merge`）。

- 可以开多个窗口、建多个 worktree **并行工作**，完工后逐个合并回主干，提高效率。

## 6. Merge Conflict 合并冲突

- **成因**：两个分支修改了**同一个文件的同一行代码**，合并时 Git 无法自动判断该保留哪个 → **冲突**。
- 必须**人工决定**保留哪个分支的代码，这个动作叫**解决冲突**。传统上这是 Git 里比较繁琐的环节。
- **有了 AI 就简单了**：分支 A 把第二行改成"西瓜"，分支 B 把第二行改成"草莓" →
  提示词：**"把两个分支都合并进主干，遇到冲突就停下来让我选择怎么处理。"**
  → AI 遇到冲突后给出选项：保留任意一个 / 两个都保留 → 选择"两个都保留，西瓜在前草莓在后" → AI 按要求解决冲突，合并成功。

## 7. Git 分区（四个区 + 数据流向）

### 7.1 四个区

| 分区 | 中文 | 说明 |
|---|---|---|
| **Working Directory** | 工作区 | 你电脑磁盘上的本地文件夹 |
| **Staging Area / Index** | 暂存区 | **commit 之前的一个检查点**，用于做提交前准备 |
| **Local Repository** | 本地仓库 | `commit` 之后，改动进入这里 |
| **Remote Repository** | 远端仓库 | 一般是 GitHub（也有 GitLab、Gitee 等），用于分享或备份；**只有推上去的代码别人才能看到** |

> 大部分 Git 操作的本质，就是**在这些分区之间互相同步文件**。

### 7.2 命令与流向

| 命令 | 流向 / 含义 |
|---|---|
| `git clone` | 远端仓库 → 本地，**同时创建本地仓库和本地工作目录** |
| `git init` + `git commit` | 工作区 → 本地仓库 |
| `git push` | 本地仓库 → 远端仓库（分享进度 / 远程备份） |
| `git pull` | 远端最新改动 → 拉取并合并到本地；**等价于 `git fetch` + `git merge`**（也可分两步执行） |
| `git add` | 工作区 → 暂存区 |
| `git commit` | 暂存区 → 本地仓库 |

### 7.3 暂存区为什么"看不见"

- 传统流程：`git add` 把文件放进暂存区 → `git commit` 把暂存区所有改动提交到本地仓库。
- 现在大部分工具**淡化/隐藏了暂存区**：VS Code 里点 Commit 按钮，实际上**同时执行了 add + commit**，大幅降低操作复杂度。
- 但暂存区仍可用：改了 4 个文件时，在某个文件右侧点 **+（Stage Changes）** 只把该文件加进暂存区 → 提交时**只提交暂存区里的文件**；不手动 Stage 的话，VS Code 默认把全部文件一起 commit。

## 8. 远端仓库实战

本地仓库绑定远端有两条路：**① `git clone`（远端→本地）**、**② `git push` / Publish（本地→远端）**。

### 8.1 路线一：clone（先有远端，再拉到本地）

1. GitHub 首页 → **New repository** → 填仓库名 → 选**公开 / 私有**（公开则代码上网、人人可看；私有只有自己可见）→ 可选 README、`.gitignore`、开源许可证 → **Create**。
2. 页面上给出的链接就是仓库地址，格式里中间一段是**你的 GitHub 用户名**，最后一段是**仓库名**。复制它。
3. VS Code → 菜单 **Close Folder** 退出当前项目 → Source Control 里的 **Clone** 按钮 → 粘贴地址回车 → 选择本地存放文件夹（例：桌面）→ 确认。
4. 桌面上出现该文件夹，本地已同时有仓库与工作目录；在项目里新增文件 → commit → 点 **Publish** 推到 GitHub → 刷新网页即可看到。

> ⚠️ **`git push` 的权限前提**：你必须是该仓库的管理员，或被管理员授予了写权限。**不能往别人的仓库里 push**——要贡献开源项目走后面的 PR 流程。

### 8.2 路线二：Publish（先有本地，再建远端）

已有一些代码但**没有 `.git`** 的文件夹（还不是 Git 仓库）：
VS Code 打开它 → Source Control → **Initialize Repository** → 做一次 commit → 点 **Publish** → 填远端仓库名 → 选公开/私有（演示选私有）→ 推送成功 → 点右下角 **Open** → GitHub 上看到代码，标注 **Private**，别人访问地址看不到。

### 8.3 把远端改动同步回本地

- 场景 A（直接在网页改）：GitHub → **Add file → Create new file** → 写内容 → 右上角 **Commit changes** → 确认。此时本地还看不到。
- 本地 Source Control 里按钮显示 **Sync Changes ↓1**（向下箭头 = 远端有 1 个提交）→ 点击 → 远端提交被拉到本地，文件出现。
- 场景 B（更常见）：同事/协作者先把自己的提交推到远端，本地一般**先 `git pull`** 拉取。

### 8.4 本地分支 vs 远端分支

- 有了远端后就有了两套分支：**`origin/main`（origin = 远端仓库）** 与 **`main`（本地）**。
- 图上看：本地 main 比远端多 2 个提交 → 按钮变成 **Sync Changes ↑2**（向上箭头 = 有 2 个提交没上传）→ 点一下推送 → `origin/main` 与 `main` 指向同一提交，即**同步状态**。

## 9. GitHub 入门（仓库页导览）

### 9.1 地址规则

`github.com / {开发者名} / {仓库名}`，所有仓库都遵循这个规则。

### 9.2 页面各区块

| 区块 | 位置 | 作用 |
|---|---|---|
| **代码库** | 页面中间最显眼 | 存放整个项目源码；可点开逐层查看；右上角 **Code → Download ZIP** 打包下载，或用地址 `git clone` |
| 文件信息 | 每个文件右侧 | ① 最后一条 **commit message** ② 最后更新日期。**若所有文件都停更在很多年前 → 项目可能已无人维护** |
| **README** | 代码库下方 | GitHub 自动读取并渲染；一般说明项目做什么、解决什么问题、怎么运行使用 |
| **Releases** | 右侧栏 | 发布版本信息：版本号 + 该版本更新内容；**Assets** 里常有作者打包好的软件，下载即可直接运行 |
| **About** | Releases 上方 | 项目简介、标签、**Star 数**、开源协议等 |
| **Star** | About 内 | 类似"点赞+收藏"，反映项目热度；感兴趣就给作者点一个 |
| **Fork** | Star 左边 | **复刻**：把项目保存一份到自己名下（路径中间变成自己的用户名）。可用于深入学习源码、按需 DIY，也可把自己的修改通过 PR 合回原作者仓库，为开源"添砖加瓦" |
| **搜索框** | 页面上方 | 清空后可直接搜索**整个 GitHub** 的项目与资源 |
| **Issues** | 左上角 | 与作者讨论：**New issue** 提 bug、提新功能期待，也可帮别人解决问题。分 **open**（未解决/讨论中）与 **closed**（已解决/已结束）。**用开源项目前先搜 issue，很多坑别人已经踩过并给了方案** |

### 9.3 必会快捷键

| 按键 | 作用 |
|---|---|
| `/` | 快速打开 GitHub 搜索 |
| `T` | 快速定位到**文件搜索栏**，按文件名找文件 |
| `L` | 快速定位到**行号**（如跳到第 33 行）；选中行号后可选 **Copy line**（复制该行代码）/ **Copy permalink**（复制永久链接，便于分享代码） |
| **git blame** | 该页面看**每行代码由谁、在哪次提交中写的** |
| `?` | 打开快捷键速查表（例：`gc` = go to code，`gi` = go to issues） |
| `.` | 打开**网页版 VS Code**，可看代码、搜索、装插件、做简单查看 |

### 9.4 Codespaces：云端运行环境

- 想真正跑/调试代码：点"运行与调试" → **Continue working** → **Create new codespace** → 按需选配置（演示选 **2 核 8GB**）→ 申请到远程运行环境，直接在浏览器里改代码调代码 → 右上角 **Run** 按钮即可跑 Python 并看到输出。

## 10. GitHub 多人协作（全片重头戏）

### 10.1 一条最重要的前置纪律

> **动手改任何代码之前，先建分支，不要在主干上改。**

原因：改动都在分支上，之后从母项目（上游）同步代码时**不会产生冲突**。

### 10.2 开源贡献标准流程（没有写权限的普通人）

角色设定：**小跟班**（贡献者） vs **技术爬爬虾**（母项目管理员）。

1. **Fork**：在母项目点 Fork → **Create Fork** → 项目复制一份到自己名下（无权限直接向原仓库提交）。
2. **Clone**：复制**自己名下这份**（子项目）的地址 → VS Code → Clone → 填地址 → 本地打开。
3. **建分支**：左下角 `main` → 创建分支 → 在分支上新增一个水果。
4. **Commit + Publish**：提交后点 Publish 推到 GitHub；在网页切到对应分支即可看到这次提交。
5. **同步上游（关键准备）**：提 PR 前先把**母项目的最新改动**合并进自己的分支，确保本地已包含上游最新代码且**没有冲突**。
   - 交给 AI：先切到**自己的分支**（不要切错）→ 把母项目地址粘给它 → **"这是母项目的地址，请把母项目的最新改动先合并进当前分支，注意如果有冲突让我选择怎么处理。"**
   - AI 同步 → 遇冲突询问 → 回答"两个都保留，先香蕉在栗子" → 同步完成 → **把本地改动 push 上去**。
6. **建 PR**：进入子项目 → **Pull requests → New pull request** → **一定要选对合并方向**（子项目 `feature` → 母项目 `main`，注意箭头方向）→ **Create pull request** → 填标题（例："为水果清单增加更多水果"）→ Create。
7. **管理员侧（Code Review）**：维护者会收到邮件 → 在 Pull requests 里打开 → **Files changed** 看对方代码 → 可留下修改意见，或直接 **Merge pull request → Confirm** → 代码合入主干。
8. **结果**：母项目的水果清单多了"樱桃"，右下角贡献者里出现小助理/小跟班的名字——一次完整的开源协作闭环完成。

### 10.3 为什么 PR 前必须先同步上游

> 若 `feature` 与主干**同时**提交了代码修改，直接建 PR 很可能因改到同一文件而产生冲突。
> **正确做法**：先把主干的改动同步到 `feature` 分支 → **在本地解决冲突** → 再提交 PR。

### 10.4 PR 是什么

- **Pull Request = 拉取请求**，视频更推荐译作**合并请求**：**把一个分支的改动合并进另一个分支的提案**。
- PR 会展示两个分支之间的**代码差异**；管理员审核的过程叫 **Code Review**；确认 OK 后同意合并，贡献者的代码进入主干。
- 通用链路：**Fork → 建分支 → 改代码 commit → PR → Code Review → Merge**。

### 10.5 场景二：协作者（可省掉 Fork）

若开发者与管理员在同一公司，或管理员把他加为**协作者**：

- 管理员：**Settings → Collaborators → Add people** → 搜索对方 → **Add**；
- 对方：GitHub 首页右上角**收件箱**里有邀请 → 接受 → 即成为协作者，**有权限直接向该仓库 push**；
- 于是流程简化为：**不需要 Fork** → 拉分支 → 提交 → push 到远端 → 先合并主干最新改动 → 提 PR → 管理员审核合并。

| 场景 | 是否 Fork | 推送目标 |
|---|---|---|
| 开源项目外部贡献者 | ✅ 需要 | 自己名下仓库 |
| 同公司 / 已被加为 Collaborator | ❌ 不需要 | 母项目远端仓库 |

## 11. 三个进阶操作：cherry-pick / stash / rebase

### 11.1 Cherry-pick（拣选提交）

- 字面意思是"摘樱桃"，Git 语境里指**把指定的某几次提交挑出来**合并进目标分支。
- 例子：feature 分支上有三次提交，分别建了 `蔬菜清单`、`肉类清单`、`主食清单`；正常 merge 会三个文件全进主干。
- 需求：**只要蔬菜和主食，不要肉类** → 分别复制这两次提交的 **commit ID** → 对 AI 说 **"你把这两次提交 cherry-pick 进主干"** → 主干上只有蔬菜与主食，肉类没进来。

### 11.2 Stash（临时存储）

> ⚠️ **stash 与"暂存区（staging area）"不是一回事。**

- 场景：在 `feature` 上写代码写到一半，需要紧急切回 `main` 处理临时任务。**直接切分支会把半成品带过去**，显然不行。
- 两种解法：
  1. 先在 feature 上**做一次 commit** 再切；
  2. 用 **stash** 把没写完的代码临时存起来，切回来再取出来继续写。
- VS Code 操作：Source Control 右上角**三个点 → Stash → 起个名字（直接回车也行）** → 半成品被存起来 → 切回 `main` 干活 → 干完切回 `feature` → 选 **Pop**（取回）继续写。

### 11.3 Rebase（变基）

- 属于 Git 的进阶操作。例子：`feature` 只有一次提交 C2，`main` 有 C3、C4、C5，要把 main 合并进 feature，但**不用 merge，改用 rebase**。
- 命令（在**需要被合并的那个分支**上执行）：`git rebase main`
- **两层理解**：
  1. 从**最终效果**看：可以认为是把 `main` 合并进了 `feature`；
  2. 从**本质**看：是把 `feature` **变基**（更改地基）到 `main` 上。
- 执行后：feature 原来那条线"消失"，C2 作为一次**新的提交 C2'** 挂到 main 后面。
- ✅ **好处**：**不会产生 `Merge branch 'xxx'` 那种合并提交记录，历史线更干净。**
- ⚠️ **代价**：因为根基变了，**必须强制推送 `git push -f`**，普通推送不行。
- 🚫 **红线**：强推只适合**只有你一个人使用的分支**。如果是多人协作分支（很多同事往同一分支提交），**万万不能强推**，否则会覆盖、搞丢别人的代码。

> VS Code 里也能做：切换到待合并分支 → 分支菜单里选 **Rebase** → 按提示强推。

## 12. 概念速查表

| 术语 | 中文 | 一句话理解 |
|---|---|---|
| Repository | 仓库 | 被 Git 管理的文件夹（内含 `.git`） |
| Local / Remote | 本地 / 远端 | 自己电脑上 / 服务器上 |
| Init | 初始化 | 让 Git 接管一个文件夹 |
| `.gitignore` | 忽略清单 | 声明哪些文件不归 Git 管 |
| Commit | 提交 | 一次快照 + 一条历史记录 |
| Commit ID / Hash | 提交哈希 | 唯一标识一次提交（短 ID 取前 7 位） |
| Discard | 放弃更改 | 丢弃未提交的改动 |
| Reset | 重置 | 强制把仓库拉回某个历史提交（危险） |
| Revert | 反向提交 | 生成一次相反改动来抵消某次提交（安全） |
| Diff | 差异 | 比较两次提交/两个版本的改动 |
| Branch | 分支 | 独立开发线（本质是指针，不复制代码） |
| Merge | 合并 | 把一条分支的提交并入另一条 |
| Merge Conflict | 合并冲突 | 同一文件同一行被两边改，需人工裁决 |
| HEAD | 头指针 | 当前仓库处于哪次 commit |
| Detached HEAD | 分离头指针 | HEAD 不在任何分支上，只读查看用 |
| Worktree | 工作树 | 新分支 + 新文件夹，可并行开发 |
| Working Directory | 工作区 | 磁盘上的文件夹 |
| Staging Area / Index | 暂存区 | commit 前的检查点 |
| Clone | 克隆 | 远端仓库复制到本地 |
| Push | 推送 | 本地 → 远端（需写权限） |
| Pull | 拉取 | 远端 → 本地并合并（= fetch + merge） |
| Fetch | 获取 | 只把远端更新取下来，不合并 |
| Fork | 复刻 | 把别人仓库复制一份到自己名下 |
| Pull Request (PR) | 合并请求 | "把我的分支并进你的主干"的提案 |
| Code Review | 代码审核 | 维护者审阅 PR 的改动 |
| Collaborator | 协作者 | 被授予仓库写权限的人（可跳过 Fork） |
| Issue | 议题 | 提 bug / 需求 / 讨论 |
| Star | 星标 | 点赞+收藏，反映项目热度 |
| Release / Assets | 发布版 / 附件 | 版本号、更新说明、打包好的软件 |
| Cherry-pick | 拣选提交 | 只挑某几次提交合并过来 |
| Stash | 临时存储 | 把半成品存起来，稍后取回 |
| Rebase | 变基 | 换掉分支的"地基"，历史更干净但需强推 |
| Codespaces | 云端环境 | 浏览器里的远程开发/调试环境 |

| 目标 | 提示词 |
|---|---|

| 建远端 | 把这个项目推送到 GitHub，需要我先创建远端仓库的话告诉我怎么操作。 |

| 撤销单次提交 | 把 commit `<hash>` 这次提交撤销掉，保持其他提交不变。 |
| 比较差异 | 比较 commit `<A>` 和 `<B>` 有什么区别、改了哪些文件。 |
| 合并 | 把 `feature` 分支合并进 `master`。 |
| 处理冲突 | 把这两个分支都合并进主干，遇到冲突就停下来让我选择怎么处理。 |
| 同步上游 | 这是母项目的地址 `<url>`，请把母项目的最新改动先合并进当前分支，有冲突让我选择。 |
| 建 PR | 帮我整理这次改动的 PR 标题与描述。 |
| 拣选提交 | 把 commit `<A>` 和 `<B>` cherry-pick 进主干。 |
| stash | 把当前未完成的改动 stash 起来，我要切分支。 |
| rebase | 把当前分支 rebase 到 master 最新的提交上。 |

## 15. 全片结论

1. **概念 > 命令**：知道"我要什么效果"就能让 AI 落地，命令只是它底层执行的东西。
2. **小步提交**：AI 每完成一个小功能点就 commit，出问题随时 Discard 重做。
3. **一切改动走分支**：多人、多 agent、多 worktree 并行时，主干永远保持干净可用。
4. **危险操作只有两个**：`reset` 与强制推送 `push -f`，只在**个人分支**上用；多人分支用 `revert`。
5. **协作靠 PR + Code Review**：Fork → 分支 → 提交 → 同步上游 → PR → 审核 → 合并。
