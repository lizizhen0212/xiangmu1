# 工作流约定

> 本仓库的开发流程。动手之前先看这里。

## 一、一件事一条 issue

每个功能点开一条 issue，写清楚：背景、验收标准、范围外的东西。范围外比范围还重要——它防的是"做着做着越做越大"。

## 二、分支命名：跟 issue 号对齐

```
issue #2  →  branch feature2
issue #3  →  branch feature3
```

**为什么不按"第几个功能"数**：本仓库缺 issue #1（已被删除，GitHub 的编号不回收、不能改），所以第一个功能对应的就是 #2。分支名必须跟 issue 号一致，否则看 PR 时对不上。

## 三、动手前先出执行大纲

每次执行前先列出：

1. 要改哪些文件
2. 要跑哪些命令（尤其是 `--delete`、`--force`、`reset` 这类不可逆操作）
3. 怎么验证（测试 / 截图 / 断言）
4. 到哪一步停下等确认

大纲确认之后再执行。**不确认的内容不要顺手做。**

## 四、PR 规范

- 标题：`feat(模块): 一句话 (#issue号)`
- 正文：把 issue 的验收清单逐条勾选，末尾写 `Closes #N`（合并时自动关 issue）
- 合并后在 GitHub 上删除该 feature 分支

## 五、合并方式：一律用 Merge commit

PR 合并统一用 **Merge commit**，不用 Squash、不用 Rebase。

```text
main:       A ─────────────── M
                 \           /
featureN:         C ─ D ─ E
```

- **为什么**：保留每个原始提交和合并节点，能看清"这几笔属于同一个功能"；回滚整个功能只要 `git revert -m 1 M`，一刀切干净。
- **代价**：`main` 上会出现分叉和合并节点，功能一多图就变复杂。接受这个代价，换取开发过程的完整可追溯。
- **不追溯**：已经合并的 PR 不改。合并方式只对**未来的** PR 生效，绝不为了"换个方式"去 force push 改写 `main` 的历史。
- 合并后删除远端 feature 分支。

## 六、提交前自检

- [ ] `git status` 没有多余的未跟踪文件
- [ ] 不提交密钥、`node_modules`、构建产物（见根目录 `.gitignore`）
- [ ] 功能跑过验证，不是"看起来对"
